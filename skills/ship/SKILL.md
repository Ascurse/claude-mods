# ship — доводка готовой работы одной командой

Один вызов вместо цепочки «коммит → пуш → мерж → закрой бид → удали ветку», которую иначе приходится диктовать по шагам.

В beads-проектах `ship` на шаге FINISH замещает `superpowers:finishing-a-development-branch`: тот
удаляет воркчтри сырым `git worktree remove`, а это ломает общую базу `.beads/` — здесь шаг 8 всегда
идёт через `bd worktree remove`.

**Объём разрешения по формулировке:**
- Полная цепочка (шаги 1–9): «ship it», «/ship», «закоммить и вмержи», «закрой бид и удали воркчтри» — не спрашивать подтверждение на каждый шаг, кроме явно отмеченных ниже.
- Узкая просьба («коммит и пуш», «запушь ветку», «сделай коммит»): выполнить шаги 1–5, остановиться и перечислить, что осталось (интеграция, ревью, уборка). Воркчтри при этом не трогать — он живёт до мержа.

## Шаги

1. **Гейты.** lint/build/test в рабочем дереве. Красные — стоп, доложить с выводом, не коммитить.
2. **Ветка.** Текущая ветка `master`/`main`/`production`/деплойная → НЕ коммитить в неё; создать новую ветку от неё: имя по конвенции бида (`bd-{ID}`), если бид известен, иначе осмысленное `fix/…`|`chore/…` — и явно назвать его в отчёте.
3. **Коммит.** В diff смешаны правки нескольких бидов → сначала atomic-commit-split (REQUIRED SUB-SKILL). Иначе — один коммит.
4. **Пуш** текущей ветки на origin. Если пуш уже выполнен внутри atomic-commit-split — не пушить повторно, шаг выполнен.
   - Пуш упал по доступу (`Permission denied (publickey)`, таймаут, нет агента ключей) — **не перезапускать ту же команду и не искать обход**. Остановиться, доложить: коммит сделан локально на ветке `<branch>` (`<hash>`), пуш невозможен, нужен ключ. Биды при этом не закрывать (шаг 5 требует факта пуша).
5. **Закрыть биды** по факту пуша: `bd close {ID} --reason "Done: pushed <branch> (<hash>)"` — не дожидаясь мержа/MR; при нескольких коммитах указывать хэш коммита именно этого бида. Затем родительский эпик: все дети закрыты → закрыть эпик тем же ходом.
6. **Интеграция** — по проекту:
   - есть постоянная интеграционная ветка (названа пользователем ранее в сессии или в CLAUDE.md проекта, например `chore/frontend-improvement`) → влить туда напрямую, перегнать гейты на слитом, пуш; проверка ревью-комментариев (шаг 7) к этому пути не применяется — гейты на слитом и есть проверка;
   - иначе определить хостинг по `git remote -v`: github.com → `gh pr create`, gitlab → `glab mr create`. Открыть PR/MR можно без подтверждения; **финальный мерж PR/MR в защищённую ветку — только после явного подтверждения пользователя.**
7. **Ревью (только PR/MR-путь).** Перед мержем вытянуть комментарии (`gh pr view --json reviews,comments` / `glab mr notes`) и убедиться, что каждый закрыт коммитом или ответом; непогашенные — доложить списком вместо мержа.
8. **Уборка.** После мержа: `bd worktree remove` (не raw `git worktree`), удалить ветку локально и на origin, вернуться на исходную ветку. Несколько бидов в разных воркчтри → повторить для каждого.
9. **Отчёт** по форме из beads-workflow (`BEAD {ID} COMPLETE`).

Шаги без предмета пропускать молча: нет бида — пропустить 5; нет воркчтри — пропустить уборку воркчтри.

## Не делать

- Не коммитить в production/master/main; не мержить в них без явного подтверждения (PR/MR открыть можно, мерж — только с подтверждением).
- Не закрывать бид при красных гейтах.
- Не оставлять «сделаю мерж потом» без явной строки в отчёте, что мерж не сделан.
